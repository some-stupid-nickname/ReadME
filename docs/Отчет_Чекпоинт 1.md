# Отчет: Чекпоинт 1 — Подготовка данных

## Источники данных

Для построения системы рекомендаций книг были использованы четыре открытых датасета с платформы Kaggle:

1. [Google Books Dataset](https://www.kaggle.com/datasets/bilalyussef/google-books-dataset) — 1,299 книг с подробными метаданными
2. [Books Dataset](https://www.kaggle.com/datasets/elvinrustam/books-dataset) — коллекция книг с информацией о публикациях
3. [GoodReads 100k books](https://www.kaggle.com/datasets/mdhamani/goodreads-books-100k) — 100,000 книг с рейтингами и описаниями
4. [CMU Books Summary Dataset](https://www.kaggle.com/datasets/ymaricar/cmu-book-summary-dataset) — 16,559 книг с детальными сюжетными описаниями


## Процесс сбора и подготовки данных

### Объединение датасетов

Исходные таблицы существенно различались по структуре и формату. Каждый датасет содержал свой набор полей, использовал разные форматы дат и по-разному записывал имена авторов. Мы привели все данные к единой схеме с пятью ключевыми столбцами: `title` (название книги), `author` (автор), `publication_date` (дата публикации), `description` (описание) и `page_count` (количество страниц).

Наиболее трудоемкой оказалась обработка дат публикации. В Google Books датасет использовал формат "Month DD, YYYY" (например, "November 05, 2013"), в Books Dataset хранились отдельно месяц и год, а в CMU Books Summary встречались записи вида "YYYY-MM-DD" или просто год. Все варианты были приведены к единому формату ISO 8601 (YYYY-MM-DD) с помощью словаря соответствий для названий месяцев и функции `prepare_date()`.

Имена авторов в Books Dataset записывались в формате "Surname, Name" (например, "Colton, Larry"), что потребовало специальной обработки. Для книг с двумя авторами в формате "Author1, Name1 and Author2, Name2" применялась функция `author_preparation()`, которая разбирала такие записи и преобразовывала их в формат "Name1 Surname1, Name2 Surname2". Строки, где автоматическое преобразование не удалось, были помечены и затем отфильтрованы из финального датасета.

После объединения всех четырех источников мы удалили дубликаты по названию книги (`drop_duplicates('title')`), так как одна и та же книга могла встречаться в нескольких датасетах. Это позволило избежать избыточности в итоговой коллекции.

### Восстановление пропущенных данных

На этапе анализа качества данных выяснилось, что около 18% книг (37,718 записей) не имели описания — ключевого поля для построения RAG-системы. Еще около 1% записей содержали пропуски в поле автора. Для восстановления недостающей информации мы разработали автоматизированный процесс на основе Google Books API.

Была реализована асинхронная система запросов к API с использованием библиотек `aiohttp` и `asyncio`. Для каждой книги формировался поисковый запрос по названию (и автору, если он был известен), после чего API возвращал наиболее подходящее совпадение. Из ответа извлекались недостающие поля: описание, автор, количество страниц и дата публикации. Обработка велась батчами по 10 параллельных запросов с помощью `asyncio.Semaphore`, что позволило обработать весь массив за примерно 5 часов вместо нескольких суток при последовательных запросах.

Процесс включал механизм повторных попыток (retry logic) для обработки временных сбоев API. Если после трех попыток данные получить не удалось, запись помечалась как проблемная и требовала ручной проверки. Также фильтровались результаты на английском языке (`language == 'en'`), чтобы исключить переводные издания с описаниями на других языках.

В результате удалось восстановить описания для большинства книг. Записи, для которых не удалось найти описание даже через API (помечены как "Not known"), были удалены из финального датасета, так как без описания книгу невозможно корректно индексировать для семантического поиска.

## Структура и хранение данных

### Итоговый датасет

Финальный очищенный датасет содержит **174,467 книг** и сохранен в файле `book_data_prepared.xlsx` размером 79.1 МБ. Формат Excel был выбран для удобства просмотра и анализа данных в инструментах вроде Microsoft Excel или LibreOffice Calc.

**Схема данных:**

| Поле               | Тип данных    | Описание                                              | Обязательность |
|-------------------|---------------|-------------------------------------------------------|----------------|
| `title`           | string        | Название книги                                        | Обязательное   |
| `author`          | string        | Автор или список авторов через запятую                | Обязательное   |
| `description`     | string        | Аннотация или краткое описание сюжета                 | Обязательное   |
| `publication_date`| string        | Дата публикации в формате YYYY-MM-DD                  | Опциональное   |
| `page_count`      | float/integer | Количество страниц (nullable, может быть пустым)      | Опциональное   |

Строки с пустыми значениями в критических полях (`title`, `author`, `description`) были исключены на этапе финальной очистки, так как они не несут достаточной информации для работы RAG-системы.

### Расположение данных

Из-за большого размера файлов (более 200 МБ в сумме) данные хранятся на Google Drive с общим доступом для команды:

- **Итоговый датасет и промежуточные файлы:** [Google Drive папка data](https://drive.google.com/drive/folders/17La2w8ZsIB5Vu0nA3CGZgYhP7fqEM1hH)
  - `book_data_prepared.xlsx` (79.1 МБ) — финальный очищенный датасет
  - `added_description.xlsx` (5 МБ) — промежуточный файл с восстановленными описаниями
  - Исходные CSV/TXT файлы четырех датасетов

В репозитории Git хранится только скрипт обработки [`data/scripts/data_preparation.ipynb`](../data/scripts/data_preparation.ipynb), который документирует весь процесс трансформации данных от сырых датасетов до финальной версии.

## Подготовка данных для RAG-системы

### Векторная база данных

На основе подготовленного датасета была построена векторная база данных Qdrant. Каждая из 174,467 книг представлена в виде 384-мерного вектора (эмбеддинга), сгенерированного моделью `all-MiniLM-L6-v2` из библиотеки sentence-transformers. Эта модель обеспечивает хороший баланс между скоростью работы и качеством семантического поиска.

В качестве текста для генерации эмбеддинга использовалось поле `description` — описание книги. Именно по этим векторным представлениям будет происходить семантический поиск при работе RAG-системы: запрос пользователя также преобразуется в эмбеддинг, после чего Qdrant находит книги с наиболее близкими векторами (по косинусному расстоянию).

**Технические параметры векторной БД:**

- **Формат хранения:** SQLite (`storage.sqlite`, 514.2 МБ)
- **Модель эмбеддингов:** all-MiniLM-L6-v2 (384 измерения)
- **Количество векторов:** 174,467 (по одному на каждую книгу)
- **Расположение:** [Google Drive папка qdrant](https://drive.google.com/drive/folders/1b20o7tnXicsZcupPpUf0xjYuo2mf76Fk)

### Chunking

Для данного проекта chunking (разбиение текста на фрагменты) не требуется. В отличие от длинных документов или книжных текстов, где один документ может содержать десятки тысяч токенов, описания книг в нашем датасете достаточно компактные (в среднем 100-500 слов). Поэтому каждое описание индексируется целиком как единый документ, что упрощает архитектуру и исключает проблему потери контекста при разбиении.

### Развертывание векторной БД

Подробные инструкции по развертыванию Qdrant и загрузке векторной базы описаны в [`backend/README.md`](../backend/README.md). Там же находятся скрипты `setup_vector_db.py` для первоначальной генерации эмбеддингов и `test_vector_db.py` для проверки работоспособности поиска.

Система поддерживает два режима работы: in-memory Qdrant для быстрого локального тестирования и persistent Qdrant с хранением данных на диске для production-окружения. Файл `storage.sqlite` с Google Drive можно скачать и использовать напрямую, либо сгенерировать эмбеддинги заново из `book_data_prepared.xlsx` с помощью предоставленных скриптов.
